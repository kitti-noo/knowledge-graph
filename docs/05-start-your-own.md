# 5. เริ่มทำ KG ของตัวเอง (สำหรับคนมีไอเดีย)

บทนี้อธิบายว่าต้อง **เตรียมอะไร** ส่วนวิธี **ลงมือทำทีละคำสั่ง** พร้อมตัวอย่างที่รันได้จริง อยู่ใน[บทที่ 6](06-walkthrough.md) ไม่ต้องเขียนโค้ดเอง สิ่งที่คุณต้องเตรียมคือ **คำถาม ข้อมูล และกติกา** ซึ่ง AI คิดแทนไม่ได้ เพราะเป็นความรู้เฉพาะของงานคุณ

ตัวอย่างตลอดบทนี้คือ **แผนที่ความเชื่อมโยงของระบบค้าปลีก** (POS, RMS, ระบบคูปอง ฯลฯ)

---

## สรุป: สิ่งที่ต้องเตรียม

### A. Set-up (ทำครั้งเดียว)

| # | สิ่งที่ต้องเตรียม | ทำยังไง / ใช้ทำอะไร |
|---|---|---|
| 1 | **เครื่องที่รันได้** | ติดตั้ง [uv](https://docs.astral.sh/uv/) และ [Ollama](https://ollama.com) แล้ว clone repo นี้ รัน `uv sync` จากนั้นลอง `uv run main.py ingest examples/thai-tourism/sample.txt --reset` ให้ผ่านก่อน |
| 2 | **ตัดสินใจเรื่อง model** | ถ้าข้อมูลเป็นข้อมูลภายในบริษัท ให้เช็ก policy ก่อนว่าส่งขึ้น cloud model ได้ไหม (ดูข้อ 3.5) ถ้าไม่ได้ ให้ใช้ model ที่รันในเครื่อง |
| 3 | **AI ที่ช่วยเขียนโค้ด** (ไม่บังคับ) | เช่น Claude Code คำสั่งพื้นฐานมีให้แล้ว ใช้ AI เฉพาะตอนต้องการความสามารถเพิ่ม (ขั้นที่ 4.2) |
| 4 | **โฟลเดอร์ข้อมูลของโดเมน** | สร้าง `domains/<ชื่อโดเมน>/` แล้ววางไฟล์ตามข้อ B ด้านล่าง (ดู[ข้อควรระวังเรื่องที่เก็บข้อมูล](#35-ข้อควรระวังเรื่องข้อมูลบริษัท)) |
| 5 | **คนตรวจ (domain expert)** | 1–2 คนที่รู้จักระบบจริง นัดไว้ช่วงรอบแรก ช่วยดูกราฟและตรวจคำตอบ |

### B. ข้อมูลที่ต้องเตรียม (5 ไฟล์)

```
domains/retail/
├── questions.md      ① คำถาม + คำตอบที่ถูก        ← ทำก่อนอย่างอื่น
├── ontology.md       ② ชนิด entity + relation ที่อนุญาต
├── entities.csv      ③ รายชื่อ entity ทางการ + ชื่อเล่น
├── triples.csv       ④ ความสัมพันธ์ (ข้อมูลหลัก)
└── docs/*.md         ⑤ เอกสารข้อความ (เสริม, ถ้ามี)
```

| # | ไฟล์ | จำเป็น? | ใครทำ | เสร็จเมื่อ |
|---|---|---|---|---|
| ① | `questions.md` | ✅ | เจ้าของไอเดีย | มี 10–20 ข้อ และทุกข้อมีคำตอบที่ถูกเขียนไว้ |
| ② | `ontology.md` | ✅ | เจ้าของไอเดีย | type ไม่เกิน ~6 และ relation ไม่เกิน ~10 พร้อมคำอธิบาย |
| ③ | `entities.csv` | ✅ | เจ้าของไอเดีย + คนในทีม | มีครบทุกระบบใน flow แรก |
| ④ | `triples.csv` | ✅ | คนในทีม (หรือแปลงจาก integration list) | ตอบ questions.md ได้ราว 80% |
| ⑤ | `docs/*.md` | ไม่บังคับ | ใครก็ได้ | ใช้เติมสิ่งที่ตารางไม่มี |

## รูปแบบข้อมูลแต่ละไฟล์

### ① `questions.md` — คำถาม + คำตอบที่ถูก

ต้องมี **คำตอบที่ถูกต้อง** เขียนไว้ด้วย ไม่อย่างนั้นจะวัดไม่ได้ว่ากราฟตอบถูกหรือผิด

```markdown
## Q1: ถ้า RMS ล่ม ระบบไหนได้รับผลกระทบ
คำตอบ: POS, E-commerce, ERP (ราคาไม่อัปเดต)

## Q2: คูปองถูก validate ที่ระบบไหน ต้องพึ่งระบบอะไร
คำตอบ: Coupon Engine โดยพึ่ง CRM (เช็กสิทธิ์สมาชิก)
```

### ② `ontology.md` — กติกาของกราฟ

เขียนเป็นตาราง relation ต้องระบุว่า **ชี้จาก type ไหนไป type ไหน**

```markdown
## Entity types
| Type       | ความหมาย                     | ตัวอย่าง               |
|------------|-----------------------------|-----------------------|
| System     | ระบบงาน                      | POS, RMS, CRM         |
| DataObject | ข้อมูลที่ส่งระหว่างระบบ           | Price, Coupon         |
| Interface  | ช่องทางส่งข้อมูล                 | Price batch 02:00     |
| Team       | ทีมเจ้าของ                     | ทีม CRM               |

## Relations
| Relation   | จาก → ไป              | ความหมาย                   |
|------------|----------------------|---------------------------|
| SENDS_TO   | System → System      | ส่งข้อมูลให้                 |
| PRODUCES   | System → DataObject  | เป็นต้นทางของข้อมูล           |
| CONSUMES   | System → DataObject  | ใช้ข้อมูล                    |
| VIA        | DataObject → Interface | ส่งผ่านช่องทาง             |
| DEPENDS_ON | System → System      | ทำงานไม่ได้ถ้าไม่มี            |
| OWNED_BY   | System → Team        | ทีมที่ดูแล                   |
```

### ③ `entities.csv` — รายชื่อทางการ (กันชื่อซ้ำ)

ไฟล์นี้แก้ปัญหาอันดับหนึ่งของ KG คือ **สิ่งเดียวกันแต่ชื่อไม่ตรงกัน** ([บทที่ 4](04-limitations.md#1-entity-resolution--สิ่งเดียวกัน-แต่กลายเป็นหลาย-node))

```csv
name,type,aliases,owner,description
POS,System,ระบบ POS|เครื่องคิดเงิน|pos system,ทีม Store IT,ระบบขายหน้าร้าน
RMS,System,Retail Merchandising|ระบบจัดการสินค้า,ทีม Merch IT,master สินค้าและราคา
Coupon Engine,System,ระบบคูปอง|Promo X,ทีม CRM,สร้างและ validate คูปอง
CRM,System,ระบบสมาชิก,ทีม CRM,ข้อมูลสมาชิกและแต้ม
Price,DataObject,ราคา|ราคาขาย,,ราคาขายปลีกต่อ SKU
```

- `name` คือชื่อทางการที่ **ทุกไฟล์ต้องใช้ตรงกัน**
- `aliases` คือชื่ออื่นที่คนเรียก คั่นด้วย `|` ใช้ให้ระบบ (หรือ LLM) map ชื่อเล่นกลับมาเป็นชื่อทางการ

### ④ `triples.csv` — ความสัมพันธ์ (ข้อมูลหลัก)

**หนึ่งแถว = หนึ่งความสัมพันธ์**

```csv
subject,relation,object,note,source
RMS,PRODUCES,Price,,interface-list.xlsx
RMS,SENDS_TO,POS,ส่งราคาและ product master,interface-list.xlsx
Price,VIA,Price batch 02:00,ไฟล์ CSV ผ่าน SFTP,คุยกับพี่ A ทีม Merch IT
POS,SENDS_TO,Coupon Engine,validate คูปองตอนชำระเงิน,Confluence: Coupon flow
Coupon Engine,DEPENDS_ON,CRM,เช็กสิทธิ์สมาชิก,INC-1234
```

กฎ:

| กฎ | ทำไม |
|---|---|
| `subject` / `object` ต้องมีใน `entities.csv` คอลัมน์ `name` | กันกราฟแตกเป็นหลาย node |
| `relation` ต้องมีใน `ontology.md` | กันชื่อ relation ไม่สม่ำเสมอ |
| ไม่ต้องใส่ type ซ้ำ เพราะดึงจาก `entities.csv` ได้ | ลดงานและลดจุดที่จะกรอกผิด |
| ใส่ `source` ทุกแถว | ย้อนกลับไปตรวจได้ |
| เวลา ความถี่ หรือเวอร์ชัน ให้ใส่ใน `note` ไม่ต้องสร้างเป็น node | กันปัญหาแบบ `พ.ศ. 2534` ในบทที่ 4 |
| ทิศทางต้องถูก: `A SENDS_TO B` คือ A เป็นผู้ส่ง | ถ้ากลับทิศ impact analysis จะผิดทั้งหมด |

### ⑤ `docs/*.md` — เอกสารข้อความ (ถ้ามี)

| ควร | ไม่ควร |
|---|---|
| ไฟล์ `.md` หรือ `.txt` (UTF-8) | PDF, Word หรือรูป (ให้แปลงเป็นข้อความก่อน) |
| หนึ่งไฟล์ = หนึ่งเรื่อง/flow | รวมทุกอย่างไว้ไฟล์เดียว |
| ย่อหน้าสั้น เว้นบรรทัดระหว่างย่อหน้า | ย่อหน้ายาวเป็นหน้า (ระบบตัด chunk ตามบรรทัดว่าง) |
| ใช้ชื่อจาก `entities.csv` ทุกครั้ง | สรรพนาม ("ตัวนี้", "มัน") หรือชื่อเล่น |
| หนึ่งประโยค = หนึ่งความสัมพันธ์ | "ส่งไปให้อีกตัวทุกคืน" |
| ไม่มีความลับ (password, key, ข้อมูลลูกค้า) | copy log หรือ config มาทั้งก้อน |

> ถ้าทำได้ ให้ใช้ ④ เป็นหลัก ส่วน ⑤ ใช้เติมเท่านั้น ข้อมูลในตารางแม่นยำ 100% ส่วนข้อมูลจากเอกสารขึ้นอยู่กับว่า LLM ดึงได้ครบแค่ไหน

## ขั้นที่ 0 — เช็กก่อนว่างานนี้เหมาะกับ KG ไหม

KG เหมาะเมื่อคำถามเป็นเรื่อง **"อะไรเชื่อมกับอะไร"** มากกว่า "เอกสารไหนพูดถึงอะไร"

| สัญญาณว่าเหมาะ | สัญญาณว่าไม่ต้องใช้ KG |
|---|---|
| คำถามต้องไล่ต่อหลายทอด ("ถ้า A ล่ม ใครกระทบต่อ") | คำถามตอบได้จากเอกสารเดียว ("วิธีตั้งค่า POS") |
| มี "สิ่ง" ชัดเจน: ระบบ ทีม ข้อมูล API | ข้อมูลเป็นบทความหรือความเห็นเป็นหลัก |
| ความรู้กระจายอยู่หลายแหล่ง หลายทีม | ข้อมูลอยู่ในตารางเดียวอยู่แล้ว และใช้ SQL ก็พอ |

ระบบค้าปลีกเหมาะมาก เพราะแต่ละระบบส่งข้อมูลต่อกันเป็นทอดๆ และไม่มีใครรู้ภาพรวมทั้งหมดคนเดียว

## ขั้นที่ 1 — เขียนคำถามที่อยากให้ตอบได้ (สำคัญที่สุด)

**เริ่มจากคำถาม ไม่ใช่เริ่มจากข้อมูล** คำถามจะเป็นตัวบอกว่าต้องเก็บ entity และ relation อะไร ให้เขียนไว้ 10–20 ข้อ เป็นภาษาที่คนในทีมใช้ถามกันจริง

ตัวอย่างสำหรับระบบค้าปลีก:

| ประเภท | คำถาม |
|---|---|
| Impact analysis | ถ้า RMS ล่ม ระบบไหนได้รับผลกระทบบ้าง |
| Data lineage | ราคาสินค้าที่ขึ้นบนหน้าจอ POS มาจากระบบไหน ผ่านอะไรบ้าง |
| Ownership | ใครเป็นเจ้าของข้อมูลโปรโมชัน ถ้าคูปองใช้ไม่ได้ต้องติดต่อทีมไหน |
| Dependency | ระบบคูปองต้องพึ่งระบบอะไรบ้างถึงจะ validate คูปองได้ |
| Change planning | ถ้าเปลี่ยน format ของ product master ต้องแจ้งกี่ระบบ |
| Onboarding | คนใหม่อยากเข้าใจว่าการขายหนึ่งบิลวิ่งผ่านระบบอะไรบ้าง |

> ทดสอบง่ายๆ: ถ้าคำถามข้อไหน **คนในทีมต้องถามต่อกัน 2–3 คน** ถึงได้คำตอบ ข้อนั้นคือจุดที่ KG ช่วยได้มากที่สุด

คำถามชุดนี้จะใช้ซ้ำในขั้นที่ 5 เป็น **ข้อสอบ** สำหรับวัดว่ากราฟใช้งานได้จริงหรือยัง

## ขั้นที่ 2 — ออกแบบ ontology (entity + relation)

ดูจากคำถามในขั้นที่ 1 ว่าต้องมี "สิ่ง" อะไรบ้าง และเชื่อมกันแบบไหน **จำกัดจำนวนให้น้อยไว้ก่อน** เพิ่มทีหลังได้ ถ้าไม่จำกัดตั้งแต่แรก จะเจอปัญหาแบบใน[บทที่ 4](04-limitations.md) ที่ relation เดียวกันมีถึงสามชื่อ

### Entity types (ตัวอย่าง)

| Type | ตัวอย่าง | หมายเหตุ |
|---|---|---|
| `System` | POS, RMS, Coupon Engine, CRM, ERP, E-commerce, WMS | ระบบหลัก |
| `DataObject` | Product Master, Price, Promotion, Coupon, Sales Transaction, Member, Stock | "ข้อมูล" ที่วิ่งระหว่างระบบ |
| `Interface` | Price API, ไฟล์ batch ราคาตอนตีสอง, Kafka topic `sales-events` | ช่องทางที่ข้อมูลวิ่งผ่าน |
| `Team` | ทีม Merchandising IT, ทีม CRM, Vendor ภายนอก | เจ้าของหรือผู้ดูแล |
| `Channel` | หน้าร้าน, แอป, เว็บ, LINE OA | (ถ้าคำถามเกี่ยวกับช่องทางขาย) |

### Relations (ตัวอย่าง)

| Relation | อ่านว่า | ตัวอย่าง |
|---|---|---|
| `SENDS_TO` | ระบบ A ส่งข้อมูลให้ระบบ B | `(RMS) -SENDS_TO-> (POS)` |
| `PRODUCES` | ระบบสร้างหรือเป็นต้นทางของข้อมูล | `(RMS) -PRODUCES-> (Price)` |
| `CONSUMES` | ระบบใช้ข้อมูล | `(POS) -CONSUMES-> (Price)` |
| `VIA` | การส่งข้อมูลผ่านช่องทางใด | `(Price) -VIA-> (ไฟล์ batch ราคาตอนตีสอง)` |
| `DEPENDS_ON` | ระบบทำงานไม่ได้ถ้าไม่มีอีกระบบ | `(Coupon Engine) -DEPENDS_ON-> (CRM)` |
| `OWNED_BY` | ใครดูแล | `(Coupon Engine) -OWNED_BY-> (ทีม CRM)` |
| `USED_IN` | ระบบใช้ในช่องทางใด | `(POS) -USED_IN-> (หน้าร้าน)` |

**เคล็ดลับ**

- ตั้งชื่อ relation ให้อ่านจากซ้ายไปขวาแล้วเป็นประโยคได้
- ถ้าสงสัยว่าควรเป็น entity หรือ attribute ให้ถามตัวเองว่า "จะถามคำถามที่ **เริ่มจาก** สิ่งนี้ไหม" ถ้าจะถาม ให้เป็น entity ถ้าไม่ ให้เป็น attribute เช่น "เวลาที่ batch รัน" ควรเป็น attribute ของ Interface ไม่ต้องเป็น node
- วันที่ เวอร์ชัน และตัวเลข ควรเป็น attribute เกือบทุกครั้ง

## ขั้นที่ 3 — เตรียมข้อมูล

### 3.1 หาแหล่งข้อมูล

| แหล่ง | ได้อะไร | ความยาก |
|---|---|---|
| **Integration list / interface spreadsheet** (ถ้ามี) | ระบบไหนส่งอะไรให้ใคร ผ่านช่องทางไหน | ง่ายมาก เพราะเป็นตารางอยู่แล้ว |
| Architecture diagram (draw.io, Visio, รูปใน Confluence) | ภาพรวมการเชื่อมต่อ | ต้องถอดเป็นข้อความหรือตาราง |
| API spec (OpenAPI/Swagger), รายการ Kafka topic, ตาราง batch job | interface จริงที่ใช้งานอยู่ | ปานกลาง |
| เอกสารระบบ หรือหน้า Confluence ของแต่ละทีม | คำอธิบายและบริบท | ใช้ LLM ดึงได้ |
| Incident report / postmortem | dependency จริงที่เคยทำให้ระบบพัง | ใช้ LLM ดึงได้ และมีค่ามาก |
| **สัมภาษณ์คนในทีม** | สิ่งที่ไม่มีใครเขียนไว้ | ต้องจดเป็นข้อความเอง |

### 3.2 ข้อมูลมีสองแบบ ใช้คนละวิธี

```
ข้อมูลมีโครงสร้าง (ตาราง)      ──▶  แปลงเป็น triples ตรงๆ  ──┐
                                   (ไม่ต้องใช้ LLM)          ├──▶  กราฟเดียวกัน
ข้อมูลไม่มีโครงสร้าง (เอกสาร)   ──▶  ให้ LLM ดึง triples    ──┘
```

**ถ้ามีตารางอยู่แล้ว อย่าให้ LLM อ่าน** ให้แปลงเป็น triples ตรงๆ จะแม่นยำ 100% เร็วกว่า และไม่มีค่าใช้จ่าย ใช้ LLM เฉพาะกับเอกสารที่เป็นข้อความเท่านั้น

สำหรับเรื่องระบบค้าปลีก แหล่งหลักควรเป็น **ตาราง** แล้วเสริมด้วยเอกสาร

### 3.3 ทำตาราง

รูปแบบไฟล์และกฎอยู่ใน[รูปแบบข้อมูลแต่ละไฟล์](#รูปแบบข้อมูลแต่ละไฟล์) ด้านบน (ไฟล์ ③ `entities.csv` และ ④ `triples.csv`) วิธีทำที่ง่ายที่สุดคือ

1. ทำใน Google Sheets หรือ Excel โดยแยกเป็นสองชีต: `entities` และ `triples`
2. ในชีต `triples` ตั้งคอลัมน์ `subject` / `object` เป็น **dropdown ที่ดึงจากชีต `entities`** และคอลัมน์ `relation` เป็น dropdown จาก ontology วิธีนี้กันการสะกดผิดได้เกือบหมด
3. ถ้ามี integration list อยู่แล้ว ให้ AI ช่วยแปลงเป็น `triples.csv` ได้ แต่ต้องตรวจทิศทางของ `SENDS_TO` ทุกแถว
4. Export แต่ละชีตเป็น **CSV (UTF-8)** ไม่ใช่ `.xlsx` เพื่อให้ภาษาไทยไม่เพี้ยน และ diff ใน git ได้

### 3.4 ถ้าเป็นเอกสาร เขียนยังไงให้ LLM ดึงได้ดี

จากบทที่ 4 เราเห็นแล้วว่า **ถ้าข้อความไม่ได้บอกความสัมพันธ์ตรงๆ LLM ก็จะไม่ดึงออกมา** ถ้าต้องจดโน้ตจากการสัมภาษณ์ ให้เขียนแบบนี้:

| ❌ เลี่ยง | ✅ ใช้ |
|---|---|
| "ตัวนี้ส่งไปให้อีกตัวทุกคืน" | "RMS ส่งไฟล์ราคาให้ POS ทุกคืนเวลา 02:00" |
| "ระบบคูปอง (เดิมชื่อ Promo X) ..." แล้วย่อหน้าต่อไปเรียก "Promo X" | ใช้ชื่อเดียวตลอดทั้งเอกสาร |
| "ถ้ามันล่ม หน้าร้านจะลำบาก" | "ถ้า Coupon Engine ล่ม POS จะรับคูปองไม่ได้" |

กฎสั้นๆ: **หนึ่งประโยค = หนึ่งความสัมพันธ์ และใช้ชื่อเต็มทุกครั้ง ไม่ใช้สรรพนาม**

### 3.5 ข้อควรระวังเรื่องข้อมูลบริษัท

model เริ่มต้นใน repo นี้ (`gemma4:31b-cloud`) **รันบน cloud** หมายความว่าข้อความที่ ingest จะถูกส่งออกจากเครื่อง ก่อนใส่ข้อมูลจริงของบริษัท ให้ทำอย่างใดอย่างหนึ่ง:

- เช็ก policy ของบริษัทว่าส่งข้อมูลประเภทนี้ออกไปได้หรือไม่
- เปลี่ยนไปใช้ model ที่รันในเครื่อง (เช่น `KG_MODEL=qwen3:8b`) ซึ่งช้ากว่าและแม่นยำน้อยกว่า แต่ข้อมูลไม่ออกจากเครื่อง
- ข้อมูลที่เป็นตาราง (③ ④) ไม่ต้องผ่าน LLM อยู่แล้ว

และอย่าใส่ข้อมูลลับลงในกราฟ เช่น password, API key หรือข้อมูลลูกค้า

**ที่เก็บไฟล์ข้อมูล:** repo นี้มีแค่ engine ตัวอย่าง และคู่มือ ข้อมูลจริงของบริษัท **ห้าม commit ลง repo นี้**

| ช่วง | เก็บที่ไหน |
|---|---|
| ลองเล่นในเครื่อง | `domains/<ชื่อ>/` ใน repo นี้ (ถูก `.gitignore` ไว้ ไม่ขึ้น GitHub) |
| ใช้งานจริง / แชร์กับทีม | private repo แยกใน org ของบริษัท แล้วชี้เข้ามาด้วย `--domain ../<repo นั้น>` |

## ขั้นที่ 4 — Set-up โปรเจกต์สำหรับข้อมูลใหม่

### 4.1 จัดโฟลเดอร์

```
domains/
  retail/
    questions.md         ← ① คำถาม + คำตอบที่ถูก (ใช้เป็นข้อสอบ)
    ontology.md          ← ② entity types + relations
    entities.csv         ← ③ ชื่อทางการ + ชื่อเล่น
    triples.csv          ← ④ ความสัมพันธ์
    docs/                ← เอกสารข้อความ (.txt / .md)
      coupon-flow.md
      interview-merch-it.md
```

### 4.2 คำสั่งที่มีให้แล้ว และเมื่อไหร่ต้องให้ AI เขียนเพิ่ม

ความสามารถสำหรับโดเมนใหม่ **มีอยู่ใน repo แล้ว** ใช้ได้ทันทีโดยไม่ต้องเขียนโค้ด (ดูวิธีใช้ทีละขั้นใน[บทที่ 6](06-walkthrough.md))

| คำสั่ง | ทำอะไร |
|---|---|
| `ingest-csv --domain <dir>` | โหลด entities.csv + triples.csv เข้ากราฟโดยไม่ใช้ LLM และตรวจชื่อ ทิศทาง และ relation ให้ |
| `ingest --domain <dir> <files>` | ให้ LLM อ่านเอกสาร โดยล็อกให้ใช้ ontology แปลงชื่อเล่นเป็นชื่อทางการ และรายงาน entity ใหม่ |
| `impact --domain <dir> <system>` | ถ้าระบบนี้ล่ม ใครกระทบ (เดินกราฟล้วน ไม่ใช้ LLM) |
| `eval --domain <dir>` | ถามทุกข้อใน questions.md แล้วเทียบกับคำตอบที่ถูก |
| `ask` / `viz` / `stats --domain <dir>` | เหมือนเดิม แต่ใช้กราฟของโดเมนนั้น |

**ให้ AI เขียนเพิ่มเมื่อ** ต้องการความสามารถที่ยังไม่มี ตัวอย่าง prompt:

```text
ใน repo knowledge-graph นี้ (อ่าน docs/ ก่อน):
- เพิ่มคำสั่ง `import-openapi <file> --domain domains/retail` ที่อ่าน OpenAPI spec
  แล้วสร้างแถวใน triples.csv (System -[PRODUCES]-> DataObject, DataObject -[VIA]-> Interface)
  ให้เขียนเป็นไฟล์ triples.generated.csv ให้คนตรวจก่อน ห้ามเขียนทับ triples.csv
```

```text
- เพิ่มคำสั่ง `path --domain <dir> <A> <B>` ที่หาเส้นทางสั้นที่สุดระหว่างสอง entity
  โดยไม่ใช้ LLM (ใช้ nx.all_shortest_paths บนกราฟแบบไม่มีทิศทาง)
```

```text
- เพิ่ม `export-neo4j --domain <dir>` ที่เขียนไฟล์ .cypher (MERGE node และ edge พร้อม note/source)
```

หลักการที่ควรบอก AI ทุกครั้ง: **ข้อมูลที่ AI สร้างให้ต้องผ่านการตรวจของคนก่อนเข้ากราฟ** และ **CSV เป็นต้นฉบับ** ห้ามแก้กราฟตรงๆ

## ขั้นที่ 5 — ทำทีละรอบ ตรวจ แล้วขยาย

```
เริ่มเล็ก (5–10 ระบบ) ──▶ ingest ──▶ ดูกราฟ (viz) ──▶ ถามคำถามจาก questions.md
      ▲                                                       │
      └──── แก้ข้อมูล / ontology / ชื่อ ◀──── ตอบผิดเพราะอะไร? ◀─┘
```

1. **เริ่มจาก flow เดียว** เช่น "การขายหนึ่งบิลที่ใช้คูปอง" ซึ่งเกี่ยวกับระบบ 5–6 ตัว ยังไม่ต้องทำทั้งบริษัท
2. **เปิด `viz` ให้คนในทีมดู** คนที่รู้จักระบบจะชี้ได้ทันทีว่า "เส้นนี้ผิด" หรือ "ขาดเส้นนี้" วิธีนี้เป็นการตรวจที่ได้ผลที่สุด
3. **ถามคำถามจาก `questions.md`** ด้วย `-v` ถ้าตอบผิด ให้ดู facts ว่าผิดเพราะอะไร
   - ไม่มีเส้นที่ต้องใช้ → เพิ่มข้อมูล
   - มีเส้นแต่ node แตก → แก้ชื่อให้ตรงกัน
   - relation ชื่อไม่ตรง ontology → แก้ prompt หรือ CSV
4. ตอบได้ราว 80% แล้วค่อยขยายไป flow ถัดไป

### อาการที่ต้องระวัง

| อาการ | สาเหตุที่พบบ่อย |
|---|---|
| `stats` เห็นระบบเดียวกันหลาย node (`POS`, `ระบบ POS`, `pos system`) | ชื่อไม่ตรงกัน ให้ทำตาราง alias |
| กราฟมี node เยอะมากแต่เชื่อมกันน้อย | ontology หลวมเกินไป หรือเอกสารไม่ได้บอกความสัมพันธ์ตรงๆ |
| ตอบได้แต่ไม่ครบ | `--hops` น้อยเกินไป หรือข้อมูลยังไม่ครบ |
| ตอบมั่นใจแต่ผิด | ดู facts ใน `-v` ถ้า facts ไม่ได้บอกแบบนั้น แสดงว่า LLM เดาเอง (แบบตัวอย่างถนนข้าวสารในบทที่ 4) |

- [ ] ① `questions.md` — 10–20 ข้อ ทุกข้อมีคำตอบที่ถูก

- [ ] export เป็น CSV UTF-8 ไม่ใช่ `.xlsx`
