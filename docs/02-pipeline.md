# 2. Pipeline ใน repo นี้

```
                 ┌────────── ingest ──────────┐
sample.txt ─▶ chunk ─▶ LLM extract ─▶ triples ─▶ build graph ─▶ graph.json
                  extract.py                          graph.py

                 ┌──────────────────── ask ─────────────────────┐
question ─▶ find seeds (LLM) ─▶ k-hop subgraph ─▶ facts ─▶ LLM answer
            query.py              graph.py                 query.py
```

| ไฟล์ | หน้าที่ |
|---|---|
| [kg/llm.py](../kg/llm.py) | เรียก Ollama และ parse JSON ที่ได้กลับมา (เผื่อไว้กรณี model ห่อด้วย ```` ```json ````) |
| [kg/extract.py](../kg/extract.py) | ขั้นที่ 1: ข้อความ → triples |
| [kg/graph.py](../kg/graph.py) | ขั้นที่ 2: triples → กราฟ NetworkX รวมถึง save/load, k-hop และ visualize |
| [kg/query.py](../kg/query.py) | ขั้นที่ 3: คำถาม → คำตอบ (GraphRAG) |
| [main.py](../main.py) | CLI: `ingest`, `ask`, `viz`, `stats` |

---

## ขั้นที่ 1 — Extract: ข้อความ → triples

**Chunk.** `chunk()` ตัดข้อความตามย่อหน้า (`\n\n`) แต่ละก้อนยาวไม่เกิน 1500 ตัวอักษร เพื่อให้ LLM โฟกัสได้ และไม่ให้ข้อความยาวเกิน context ของ model

**ให้ LLM ดึงโครงสร้าง.** แต่ละ chunk จะถูกส่งไปพร้อม system prompt ที่บอกให้ตอบเป็น JSON:

```json
{"triples": [{"subject": "...", "subject_type": "...",
              "relation": "...", "object": "...", "object_type": "..."}]}
```

ตัวอย่าง: ประโยค *"จังหวัดสุราษฎร์ธานีในภาคใต้มีเกาะสมุยและเกาะพะงัน ซึ่งมีชื่อเสียงจากงานฟูลมูนปาร์ตี้"* ได้ออกมา 4 triples:

```
(จังหวัดสุราษฎร์ธานี) -[LOCATED_IN]-> (ภาคใต้)
(เกาะสมุย)          -[LOCATED_IN]-> (จังหวัดสุราษฎร์ธานี)
(เกาะพะงัน)         -[LOCATED_IN]-> (จังหวัดสุราษฎร์ธานี)
(ฟูลมูนปาร์ตี้)       -[HELD_AT]->    (เกาะพะงัน)
```

สังเกตว่า LLM รู้ว่า "ซึ่งมีชื่อเสียงจากงานฟูลมูนปาร์ตี้" หมายถึงเกาะพะงัน ไม่ใช่เกาะสมุย ความเข้าใจภาษาแบบนี้คือเหตุผลที่ใช้ LLM แทนการเขียน rule เอง

กฎใน prompt ซึ่งเป็นตัวกำหนดคุณภาพของกราฟ:

- ใช้ **ชื่อเต็ม** ของ entity ไม่ใช้สรรพนาม (เช่นไม่ใช้ "ที่นี่" แต่ใช้ชื่อจริง)
- ชื่อ entity ใช้ภาษาเดียวกับต้นฉบับ (ภาษาไทยก็คงเป็นภาษาไทย)
- type มาจากรายการสั้นๆ ที่กำหนดไว้ เช่น `Person, Place, Organization, ...`
- relation เป็นคำกริยาแบบ `UPPER_SNAKE_CASE` เช่น `LOCATED_IN`
- ดึงเฉพาะสิ่งที่ข้อความบอก ห้ามเดา

ทุก triple จะได้ `source_chunk` ติดไว้ด้วย เพื่อย้อนกลับไปดูได้ว่ามาจากย่อหน้าไหน

> **เทียบกับ RAG ปกติ:** RAG ตัด chunk แล้ว *embed* เป็นเวกเตอร์ ส่วน KG ตัด chunk แล้ว *ดึงโครงสร้าง* ออกมา ขั้นนี้แพงกว่า (ต้องเรียก LLM ทุก chunk) แต่ได้ข้อมูลที่ query เชิงความสัมพันธ์ได้

## ขั้นที่ 2 — Build: triples → กราฟ

ใช้ `nx.MultiDiGraph` ของ NetworkX:

- **Di** (directed) — edge มีทิศทาง
- **Multi** — node คู่เดียวกันมี edge ได้หลายเส้น เช่น `(ยูเนสโก) -REGISTERED-> (X)` และ `(ยูเนสโก) -VISITED-> (X)` อยู่พร้อมกันได้

ส่วนที่สำคัญที่สุดคือ `key()`:

```python
def key(name: str) -> str:
    return " ".join(name.lower().split())
```

ฟังก์ชันนี้แปลงชื่อเป็น id ของ node ชื่อที่ได้ key เดียวกันจะ **รวมเป็น node เดียว** เช่น `จังหวัดสุราษฎร์ธานี` ที่ปรากฏใน 3 triples ข้างบนจะกลายเป็น node เดียว เกาะสมุยกับเกาะพะงันจึง "อยู่จังหวัดเดียวกัน" ในกราฟ นี่คือ *entity resolution* แบบง่ายที่สุด ถ้าทำได้ไม่ดี กราฟจะแตกเป็นเกาะๆ ที่ไม่เชื่อมกัน (ดู[บทที่ 4](04-limitations.md))

`build()` ยังกัน edge ซ้ำด้วย ถ้ามี relation เดียวกันระหว่าง node คู่เดิมอยู่แล้ว จะไม่เพิ่มอีก จึงรัน `ingest` ซ้ำหลายไฟล์ได้โดยไม่เกิด edge ซ้ำ

กราฟถูกบันทึกเป็น JSON (`node_link_data`) ที่ [examples/thai-tourism/graph.json](../examples/thai-tourism/graph.json) ซึ่งเปิดอ่านได้ด้วยตา

## ขั้นที่ 3 — Ask: คำถาม → คำตอบ

ตัวอย่างคำถาม: *"ประเพณีที่ตรงกับยี่เป็งมีต้นกำเนิดที่จังหวัดใด"*

**3.1 หา seed entity** — `find_seeds()` ส่งคำถามพร้อมรายชื่อ node ทั้งหมดให้ LLM แล้วให้เลือกว่าคำถามพูดถึง node ไหน

```
seeds: ['ประเพณียี่เป็ง']
```

**3.2 ขยายเป็น subgraph** — `subgraph_facts()` ใช้ `nx.ego_graph` เก็บทุก node ที่อยู่ห่างจาก seed ไม่เกิน `hops` ก้าว (ค่าเริ่มต้นคือ 2) ขั้นนี้มองกราฟแบบ *ไม่มีทิศทาง* เพื่อให้เดินย้อน edge ได้ เช่นจาก `จังหวัดสุโขทัย` ย้อนไปหา `ประเพณีลอยกระทง` ที่ชี้เข้ามาด้วย `ORIGINATED_IN` จากนั้นแปลง edge ทั้งหมดเป็นบรรทัดข้อความ:

```
(ประเพณียี่เป็ง) -[HELD_IN]-> (จังหวัดเชียงใหม่)
(ประเพณียี่เป็ง) -[EQUIVALENT_TO]-> (ประเพณีลอยกระทง)
(ประเพณีลอยกระทง) -[ORIGINATED_IN]-> (จังหวัดสุโขทัย)
(ดอยอินทนนท์) -[LOCATED_IN]-> (จังหวัดเชียงใหม่)
...
```

facts ที่ได้จะมีทั้งส่วนที่เกี่ยวข้องและส่วนที่ไม่เกี่ยว (เช่น ดอยอินทนนท์) การคัดว่าข้อไหนใช้ตอบได้เป็นหน้าที่ของ LLM ในขั้นถัดไป

**3.3 ให้ LLM ตอบจาก facts เท่านั้น** — prompt สั่งให้ใช้แค่ facts ที่ให้มา และอธิบายเส้นทางที่เดิน:

```
คำตอบ: จังหวัดสุโขทัย
(ประเพณียี่เป็ง) -[EQUIVALENT_TO]-> (ประเพณีลอยกระทง) -[ORIGINATED_IN]-> (จังหวัดสุโขทัย)
```

ใส่ `-v` เพื่อดู seeds และ facts ที่ส่งให้ LLM ได้ ถ้าคำตอบผิด ให้ดู facts ก่อนเสมอ ปัญหาส่วนใหญ่อยู่ที่กราฟ (ดึงข้อมูลไม่ครบ หรือ node แตก) มากกว่าที่ขั้นตอบคำถาม

### ปรับ `--hops`

ลองถามว่า *"ภาพยนตร์ The Beach ถ่ายทำในจังหวัดใด"* คำตอบอยู่ห่างจาก seed (`The Beach`) 4 ก้าว

```bash
uv run main.py ask "ภาพยนตร์ The Beach ถ่ายทำในจังหวัดใด"
# → The provided facts are insufficient ... no fact linking Phi Phi Leh to a specific province.

uv run main.py ask "ภาพยนตร์ The Beach ถ่ายทำในจังหวัดใด" --hops 4
# → ภาพยนตร์ The Beach ถ่ายทำในจังหวัดกระบี่
#   (The Beach) → อ่าวมาหยา → เกาะพีพีเล → หมู่เกาะพีพี → (จังหวัดกระบี่)
```

ด้วย 2 hops ระบบเห็นแค่ถึง `เกาะพีพีเล` จึงตอบว่าข้อมูลไม่พอ ซึ่งถือว่าดี เพราะไม่เดาคำตอบเอง

| hops | ผล |
|---|---|
| 1 | facts น้อย แม่นยำ แต่ตอบคำถาม multi-hop ไม่ได้ |
| 2 | ค่าเริ่มต้น พอสำหรับคำถามส่วนใหญ่ |
| 3+ | facts เยอะขึ้นแบบทวีคูณ โดยเฉพาะถ้าเดินผ่าน node ศูนย์กลางอย่าง `ยูเนสโก` อาจเกิน context หรือทำให้ LLM สับสน |
